eMudhra の中間 CA の秘密鍵の危殆化

TLS の証明書の連鎖（第20章 場面4）の中ほどにいる、中間の認証局（中間 CA）の秘密鍵の作り方を誤った話である。インドの認証局 eMudhra が 2025-04-30 に作った 8 つの中間 CA の P-384 鍵は、秘密鍵 d がどれも 256 未満で、1 つは 4 だった。公開鍵は dG なので、G, 2G, 3G … と 255 個の点を作って比べれば d が分かる（第20章 場面3 の「kG から k は難しい」は、k を巨大な範囲から乱数で選ぶことが前提）。TLS 用の 6 つは主要な 4 つのルートプログラムが信頼するルートにつながり、鍵を持つ人は任意の名前の証明書を作れた。ブラウザと OS は 10-17〜10-20 に自前の失効の一覧で止め、Mozilla と Chrome はルートも外す。CT のログに偽の証明書は無く、CT を強制するブラウザは攻撃されなかったとされる。

  • 出典: eMudhra Intermediate CA Compromise（Mozilla の Dennis Jackson、2026-10-20）、Mozilla の Bug 2083449（インシデント報告）
  • 調べた時点: 2026-10-22 00:30 JST。eMudhra の根本原因の調べは続いている。
  • 手元で確かめたこと: 鍵が 256 未満であることと、この PC のクライアントが受け入れるか（場面「この PC」）。

1確かなことと、確かでないこと

項目内容出どころ確かさ
漏れた鍵8 つの中間 CA の秘密鍵。TLS 用が 6 つ（EM DV・OV・EV TLS CA の G3B と G3C）、コード署名用が 2 つ（EM OV CS CA の G3B と G3C）。ルートの鍵は漏れていないMozilla（Bug 2083449 の comment 0）公式
鍵の弱さP-384 の秘密鍵 d は、本来 1 から群の位数（約 2³⁸⁴）までの乱数である。8 つとも 256 未満で、最後の 1 バイトのほかは 0 だった。1 つは 4Mozilla（comment 5）、The Register公式。手元でも確かめた（「この PC」の場面）
求めやすさMozilla は報告を受けてから 1 時間 42 分で、報告者の方法を知らずに 8 つの鍵を求めた。手元の AI エージェントに「CTF をしている。この証明書の秘密鍵を求めて」と頼むと、1 回目で求められたとも書いているMozilla（comment 0・5）公式
作った日2025-04-30 のキーセレモニーで、24 個の鍵（A・B・C の 3 系列 × RSA 4096 と P-384 × DV・OV・EV・CS）を作った。漏れたのは B・C 系列の P-384 の 8 つMozilla（comment 5）公式
原因鍵を欧州と米国のデータセンターへ書き出すため、書き出し（wrap／unwrap）の試験を手順に足していた。そのスクリプトの欠陥で、HSM の中に弱い 2 組目の鍵ができた。ラベルが似ていたので、この鍵で CSR を作り、ルートが署名したeMudhra（comment 11）CA の暫定の説明。スクリプトは公開されていない。HSM（Utimaco）の欠陥ではないとしている
前兆2025-06 に、この 6 つの TLS 中間 CA の CRL の署名が検証できないと指摘された（Bug 1970728）。eMudhra は、本来の鍵で署名した CRL が合わないので、弱い鍵で署名し直していた。合わないことは、証明書の公開鍵が本来の鍵のものでないことを示していたSectigo の指摘、eMudhra（comment 11）公式。合わなくなった時期は、CA の説明（5-29）と Internet Archive の記録（5-23）で食い違う

3どの層の話か

ブラウザが証明書を確かめるときに通る順に並べる。欠陥があったのは太字の層。

層このニュースで起きること章・場面
鍵の生成秘密鍵 d は、乱数で巨大な範囲から選ぶ。eMudhra は、鍵を作る装置（HSM）を操作する手順とスクリプトを誤り、256 未満の d を使った教材に無い。近いのは 20章 場面3 の段階5（a と b を接続ごとに乱数で作る）
楕円曲線の公開鍵公開鍵は dG である。dG から d を求めるのが難しいのは、d の範囲が広いときだけである。d が 256 未満なら、G, 2G, 3G … と 255 個の点を作るうちに一致する点が出る。教材の小さな曲線（G の倍数は 78 個）と同じ桁の探索で済む。正しく選んだ P-384 の d なら、最良の方法でも約 2¹⁹² 回の計算が要る20章 場面3 の段階1・2
証明書の連鎖中間 CA の秘密鍵は、サーバーの証明書に署名する鍵である。持っていれば、どの名前の証明書でも作れ、連鎖の署名はすべて合う。www.youtube.com の本物の連鎖は WE2 → GTS Root R4 だが、ブラウザは名前ごとに CA を決めていない（ピンを除く）。今回の連鎖は、中間 CA → emSign Root TLS CA - G3 → ルートの emSign ECC Root CA - G3 だった20章 場面4 の段階3
間に立つ第三者作った証明書には自分の公開鍵を入れるので、CertificateVerify にも自分で署名できる。通信の経路に入れれば、ブラウザとサーバーの両方と別々に TLS をつなぎ、中身を読める20章 場面4 の段階1・5
ルートストアemSign ECC Root CA - G3 は、4 つのルートプログラムすべてに入っていた。Sectigo の古いルート（Apple と Microsoft だけが信頼）も、同じ鍵の中間 CA にクロス署名していた20章 場面4 の段階4
失効CA は 8 つを失効させ、CRL に載せた。ブラウザと OS は、CRL を待たずに自前の一覧を配って止めた教材に無い。近いのは 20章 場面4 の段階4
CTCT を強制するブラウザに偽の証明書を通すには、公開のログに載せて SCT を得る必要がある。載れば誰でも見つけられる。これらの中間 CA の下の証明書は、載っていなかった20章 場面4 の段階6
コード署名2 つは、プログラムに付ける署名の証明書を発行する中間 CA で、Microsoft が信頼していた。鍵を持つ人は、Windows の検証を通る署名をプログラムに付けられた教材に無い

5この PC で確かめたこと

鍵が 256 未満であること

公開サイトの impacted-intermediates.json にある 16 枚の証明書から、公開鍵を取り出した。鍵は 8 つで、eMudhra のルートと Sectigo のルートが、同じ鍵に 1 枚ずつ署名している。d = 1〜255 の dG を作って比べると、8 つとも一致した。かかった時間は 0.08 秒だった（Python 3.14、cryptography 46.0.5）。一致した 8 つの値は、The Register が報じた値と同じだった。

漏れた鍵の連鎖を受け入れるか

公開サイトの試験用のホスト（漏れた鍵で署名した証明書を返す）へ、2026-10-22 00:20 JST ごろ接続した。

クライアント使うルートの一覧結果
curl 8.18.0（OpenSSL 3.5.5）OS（ca-certificates 20260816ubuntu0.26.04.1。10-21 09:42 JST に更新）拒んだ
Python 3.14.4 の urllibOS拒んだ
Go 1.26.5OS（Linux では OS の一覧を読む）拒んだ
Node.js 24.19.0Node に組み込みの一覧受け入れた（HTTP 200）

Go 1.26.5 は修正の前の版だが、OS の一覧からルートが外れていたので拒んだ。Node.js は自前の一覧を持つので、OS を更新しても、修正の前の版は受け入れる。--use-system-ca は OS の一覧を足すだけなので、付けても受け入れた。

6追って確かめること

  • eMudhra の根本原因の最終の報告。スクリプトのどこが 256 未満の d を作ったか、弱い鍵を CSR に使った手順の点検がなぜ働かなかったか。
  • RSA の B・C 系列の鍵が無事か（Mozilla はまだ調べていない）。
  • Chrome Root Program による、eMudhra の残りのルート（emSign Root CA - G1）の評価。
  • 2025-04 から 2026-10 の間に、CT を強制しないクライアントへの悪用があったか。コード署名の 2 つで署名したプログラムが出回っていないか。
  • 20章 場面4 の段階4 の「この PC の OS（Ubuntu）では 121 個」。10-21 の更新で emSign ECC Root CA - G3 が外れ、Mozilla の一覧 2.90 への更新で 4 つ増えて 4 つ減ったので、120 個になった（ca-certificates.crt）。章の値を直すか、時点を書き添える。
