## 5. 仕上げ確認の結果（19・20 章）

### 19 TCP・UDP・QUIC
- 表紙のリードで UDP も再送・速さの調整をするように読めた所を書き分けた。ISN の理由（接続ごとに変える・予測しにくくする）。入れ替わりの原因を「途中で遅れ」に（11 章の「同じ経路に流すので、まれ」と合わせる）。SACK の番号の 1 ずれ。
- CUBIC が既定の根拠を RFC 9438（2023 年）に、BBR は IETF 119（2024-03）の Google の資料（YouTube の TCP は BBRv3）に。
- UDP のチェックサムを 17 章の問い合わせの値から計算し直した（0x19b5）。ClientHello が Initial 2 個に分かれることを図に 1 行。
- 申告の事実はすべて確かめた（Chrome の QUIC と TCP の競争と失敗の記憶は Chromium のソース、PING は RFC 9308 §3.2、2013 年の公開は Chromium Blog、QUICHE の共用は README）。

### 20 TLS
- 場面4 の証明書の連鎖が、ECDSA の葉に RSA の連鎖（WR2 → GTS Root R1）を混ぜていた。2026-10-17 に Chrome 155 の securityDetails と openssl で取り直すと WE2 → GTS Root R4（ルート EC P-384、中間 EC P-256）。SCT も i.ytimg.com のものが混ざっていた。plan.md「実測の記録」も直した。
- 申告の 6 件（ルート 100 個、ECH は Chrome 117、Beauty and the Burst 2017、AES-NI 2010、X25519 は約 2^126、CT 必須）はすべて正しかった。
- 図の中の AES・GCM・RFC 7748・小さな曲線の値は Python で別に計算して一致。

### 21 HTTP
- 同じ条件で測り直した（2026-10-17、要求 201 個・約 11.3 MB、最初の画 約 2.3 秒。plan.md「実測の記録」）。申告の 4 件: SABR の「サーバーが選ぶ」は言い切りを弱めた（22 章と同じ書き方）、HTTP/2 への戻り方は Chromium のソースどおり、HPACK は Node の http2（nghttp2）で数え直して範囲内、Cookie の Domain は RFC 6265 どおり（実測も一致）。
