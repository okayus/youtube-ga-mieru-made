# 2026-10-29 第28章 コンパイラ・第29章 型で意味を表す

## 依頼

1. 「自分で定義した型と言語標準の型で違いはある？」（質問。会話で答えた。要旨は下の「調査」に含めた）
2. 「型システムの利点について追記してほしい。『引数に int を指定した関数に間違えて string 型を渡すと静的検査でエラーとなり事前にバグを防げる』といったことは個人的にあまり利点に感じない。そういう間違いをする場面が思い浮かばないから。型システムは実装したいドメインを表現し、コードに意味をもたせることがメリットだと思っている。例えば日本円を表現するときに非負整数となる yen 型を定義したり、状態遷移を関数として名前を付けたりなど。ただ、この型システムとコンパイラや CPU との知識的なつながりを持てなくて、型への理解が浅いと感じている。型システムの利点を追記する前に、コンパイラの章が必要な気がする。まず私の考えについて調査し、どういう章を差し込み・追記するべきかを考えて」
3. 提案（下）への返事: 「すべて任せる。進めて。」

## 調査（会話で示したもの）

- 持ち主の考えは、型を使った設計の確立した考え方と同じ。代表は Minsky「Effective ML」（不正な状態を表せなくする。ハーバード cs51 の講義 2010、ブログ 2011-03-09）、King「Parse, don't validate」（2019-11-05）と「Names are not type safety」（2020-11-01）、Wlaschin『Domain Modeling Made Functional』（2018、邦訳『関数型ドメインモデリング』2024）、Strom・Yemini の typestate（IEEE TSE、1986）、Fowler『Refactoring』の Primitive Obsession。
- 「int に string」と「ドメインを表す」は同じ型検査の両端。型検査が捕まえるのは型として書いた区別だけ。表し方が同じで意味が違う値の取り違えの例が Mars Climate Orbiter（力積をポンド重秒で出し、ニュートン秒として読んだ。4.45 倍。事故調査委員会の第 1 報告 1999-11-10）。
- 実証: Gao・Bird・Barr（ICSE 2017）は公開の JavaScript のバグ 400 個のうち、TypeScript と Flow の型注釈でそれぞれ 60 個（15%）を検出（測ったのは注釈を足した効果で、ドメインを型にした設計の効果ではない）。Mayer ら（OOPSLA 2012、27 人）は、文書の無い API を使う課題で静的型が速い課題と遅い課題の両方があった。
- 補う点: 円を非負にする方法は、負を表せない表し方（u64）と、カプセル化（スマートコンストラクタ。保証はモジュールに依る）の 2 通り。状態遷移の名付けも、値（enum。コンパイラは網羅性、CPU はタグ）と型（typestate。コンパイラが順番を確かめ、機械語に何も残らない）の 2 通り。
- 型とコンパイラ・CPU のつながり（rustc 1.95・LLVM 22.1.2 で確かめた）: `struct Yen(u64)` の足し算は、MIR では `fn yen_add(_1: Yen, _2: Yen) -> Yen` と Yen が残り、LLVM IR では `define noundef i64 @yen_add(i64 noundef %a, i64 noundef %b)` で消え、機械語は `lea rax, [rdi + rsi]` と `ret`。`Yen::new` の `v >= 0` は `not` と `shr rax, 63`、`checked_sub` は `sub` の借りを `setae` で読む。`Option<u64>` 16 バイト、`Option<NonZeroU64>` 8 バイト。typestate の遷移は `mov rax, rdi` / `ret`、enum の遷移はタグを読んでジャンプ表。**型だけで持つ区別はコンパイラが一度確かめて消し、値で持つ区別は CPU が実行のたびに確かめる。**

## 仕上げ確認で直した主な所

- 第29章（17 か所）
  - Mars Climate Orbiter: 「ファイルの数に単位は付いていない」を「単位はファイルの外の仕様（SIS）で決まる」に。報告書は SIS が形式と単位を決めると書くだけ。運用側（LMA）の書き方は報告書と一致。
  - 「Fowler は」→「Fowler と Beck は」（『Refactoring』の不吉な匂いの章は共著）。
  - 構造体は「欄を順に並べる」→「重ねずに並べる」（Rust の既定の並びは順を変える）。
  - 借り（CF）のリンク先を第4章 場面6 から第26章 場面3 段階3 へ（第4章は 2 の補数の加算器の話で、借りの語が無い）。
  - IFrame API の例「2 から 5 への遷移」は実際に起こりうる（cueVideoById）ので、「変数に 7 を入れても」に。
  - E0004 が出るのは `_` で残りをまとめていない match だけ、と限った。
  - 答え（場面6・要点6）の「実行時の費用は 0」を「増えない」に。enum の状態は CPU が毎回タグを読むので、そのままでは章の骨と食い違っていた。
  - ほか、図の色（物理量を d から無彩色に）、札の名前、リンクの行き先（第28章の場面）など。
  - 機械語・誤りの文・大きさは rustc 1.95.0・gcc 15.2.0・tsc 7.0.2 で取り直して一字ずつ一致。Gao らの「どちらも 60 個」は、最初の Flow 59・TypeScript 58 から判定できなかった 18 個を調べ直した後の最終の数。

- 第28章（14 か所）
  - 場面3 段階2: panic の札の "…would overflow" は MIR の assert の表示用の文で、実行して出るのは "attempt to subtract with overflow"（rustc 1.95）。札を実行時の文に。借用の検査は最適化前の MIR で行うので「この MIR の上で」を「MIR の上で」に。
  - 場面3 段階3: 「LLVM IR の型は意味の区別を持たない」は言い過ぎ（名前付きの構造体の型があり、opt-level=0 の rustc は `%Seg = type {…}` を出した）。「Ms も Bytes も同じ i64 になる」に。
  - 場面3 段階6: `biggest::<u64>` と出るのは v0 の記号のときだけ（既定の記号では nm -C が `m::biggest`）と明記。図の前提の `#[inline(never)]` をコードに書いた。
  - 場面4 段階2: MIR が ahead を呼んだまま残り LLVM が展開したのは、ahead に `#[no_mangle]` を付けた設定のため（付けないと MIR の段で `_0 = const 6160_u64` まで畳む）。本文を「図の設定では LLVM が」にし、表紙の注記に足した。
  - 場面4 段階3: .o の nm では別の関数もみな 0 番地に見えるので、cdylib にリンクした .so の nm（`00000000000116f0 T ahead` と `ahead_u`）に替えた。
  - 場面4 段階6: 「参照なら別名が無い」は &u64 どうしに当たらないので「&mut なら」に。「LLVM は型を知らず」は「LLVM は Rust の型を知らず」に。
  - 場面6 段階1: R_X86_64_PLT32 は相対の値なので「記号 twice の番地を入れよ」を「ここから記号 twice までの差を入れよ」に。段階2: プログラムヘッダ 14 個のうち LOAD が 4 個なので「ELF の読み込む部分は 4 つの区画」に。
  - 場面6 段階5: 「JIT も型を確かめる仕事は同じ」は誤り。JIT は前提の型を、作った機械語の中で実行中に確かめる。図の「作り直す」を第26章 場面4 に合わせて「捨ててバイトコードの実行に戻る」に。
  - ほか、名前解決の動き（関数の外にある欄の型 u64 は、クレートの表だけで引く）、APX（予告された拡張で 32 本）の一言、`.debug_info` は読み込まれないこと、用語表の「コンパイラ」の言い方など。
  - cargo の release の既定にあふれの検査が無いことも、この PC で確かめた。
