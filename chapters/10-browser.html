ブラウザ

アドレスバーに URL を打ってから動画が映るまでに、ブラウザは文字列を分解し、別プロセスに通信を頼み、届いた HTML を木（DOM）にし、CSS で大きさと位置を決め、画素に塗って GPU で重ねる。再生ボタンを押すと JavaScript がイベントループの上で動き、<video> と Media Source Extensions を通して動画の断片をデコーダに流し込む。この章は、第9章の OS の上で動くこの一連の処理を、Chromium の構成で追う。

構成

    文字列の部品、HSTS、ブラウザ・ネットワーク・レンダラの各プロセスへの受け渡し。

  2. 2HTML → DOM

    バイト列を文字に、トークンに、木に。<script> で止まる理由とプリロードスキャナ。

  3. 3CSS → スタイル → レイアウト

    CSSOM、カスケードと継承、ボックスの位置と大きさ。動画の箱 1280×720 が決まる。

  4. 4ペイント → 合成

    描画命令、レイヤー、タイルのラスタライズ、コンポジタ、垂直同期で画面へ。

  5. 5JavaScript とイベントループ

    V8 の JIT、1本のメインスレッド、タスクとマイクロタスク、クリックと fetch の道。

  6. 6<video> と MSE

    SourceBuffer に断片を入れ、復号して合成層へ。再生の時計とバッファリング。

    要点と用語。次の章（ネットワークの層）へ。

プロセスの分け方・スレッド名・コンパイラ名は Chromium（Chrome・Edge）のもの。Firefox・Safari も同じ段取りだが部品の名前が違う。

1URL を打つ

https://www.youtube.com/watch?v=…HSTSIPC

アドレスバーの文字列は、まず部品に分解され、送る前に https に直され、通信専用のプロセスに渡される。描画を担当するプロセスは、ネットワークにも UI にも直接触れない。

デスクトップ版 Chromium の主なプロセスは、ブラウザ・ネットワークサービス（第9章）・GPU が1つずつと、サイトごとのレンダラ。レンダラが落ちても巻き込むのはそのサイトのタブだけで、乗っ取られても他サイトのデータには届きにくい（サイト分離）。

2HTML → DOM

UTF-8トークナイザツリー構築

届いた HTML は、文字 → トークン → 木、の順に組み立てられる。この木が DOM（Document Object Model）で、JavaScript が触るのも、次の場面でレイアウトされるのもこの木。

YouTube の視聴ページの HTML は圧縮前で 1 MB を超える（2026 年時点）が、大半は埋め込みの JSON と JS。最終的に数千個になる要素の多くは、あとから JS が作る。パーサの手順は HTML 仕様が状態機械として定めていて、どのブラウザでも同じ木になる。

3CSS → スタイル → レイアウト

CSSOMカスケード1280 × 720

DOM には見た目の情報がない。CSS の規則を各ノードに当てはめて計算済みスタイルを作り、それをもとにレイアウトで位置と大きさ（px）を決める。動画が映る矩形はここで決まる。

計算済みスタイルは全ノード × 全プロパティ（数百個）あるので、ブラウザは同じ値の塊を共有して持つ。レイアウトは木を上から下へ1回なぞるのが基本で、フロート・テーブル・グリッドなど種類ごとに別のアルゴリズムが走る。

4ペイント → 合成

表示リストレイヤータイル16.7 ms

レイアウトで決まった箱を、描画命令 → レイヤー → 画素のタイル → 1枚のフレーム、と変えていく。動画のように毎フレーム変わる部分と、変わらない本文を別のレイヤーにするのが、滑らかさの要。

Chromium ではメインスレッドがペイントまで、コンポジタスレッドが合成、GPU プロセスがラスタライズと表示を担当する。この分業のおかげで、JS が重くてもスクロールと動画は止まりにくい。

5JavaScript とイベントループ

V8タスク／マイクロタスクrAF

YouTube のプレーヤーは JavaScript。メインスレッド1本の上で、イベントループがクリック・タイマー・通信の応答を1つずつ処理し、合間に描画を挟む。再生ボタンのクリックも、動画の断片の取得も、ここを通る。

タスクは1つ終わるまで割り込まれない（run-to-completion）。50 ms を超えるものは「長いタスク」と呼ばれ、その間に届いたクリックやキー入力は、終わるまで待たされる。

6<video> と Media Source Extensions

MediaSourceSourceBufferappendBuffer

動画は <video> 要素に映る。YouTube は数秒分ずつの断片を JS で取り、MSE（Media Source Extensions）の口から流し込む。画質の切り替えや先読みをブラウザ任せにしないためだ。

YouTube の映像は VP9 か AV1（古い端末は H.264）、音声は Opus か AAC で、容器は WebM か MP4。VP9・AV1 のハードウェアデコードに対応していない GPU では CPU で復号するため、高解像度で発熱が増える。

7まとめ — URL から動画の箱まで

  1. URL はスキーム・ホスト・パス・クエリに分かれ、HSTS で送信前に https に直り、ブラウザプロセスからネットワークサービスへ IPC で渡る。描画担当のレンダラは通信に直接触れない（1）。
  2. HTML はバイト列 → 文字 → トークン → 木（DOM）。同期の <script> でパーサは止まり、プリロードスキャナが先読みする（2）。
  3. CSS を CSSOM にし、カスケードと継承で計算済みスタイルを作り、レイアウトで px の矩形を決める。動画の箱 1280×720 はここで決まる（3）。
  4. ペイントで描画命令を作り、レイヤーに分け、タイルを GPU で画素にし、コンポジタが 16.7 ms ごとに1枚に重ねる。動画は専用レイヤー（4）。
  5. JS は V8 がバイトコードと JIT の機械語で走らせ、イベントループがタスク → マイクロタスク → レンダリングを繰り返す。クリックも fetch の応答もタスク（5）。
  6. プレーヤーは MSE の SourceBuffer に断片を appendBuffer し、ブラウザが復号して合成層へ。再生位置が溜めた区間の先端に追いつくと止まる（6）。
HSTSHTTP Strict Transport Security。サイトが「以後 https だけで来い」と宣言する仕組み。プリロードリストに載ったドメインは初回から書き換える。
サイト分離Chromium がサイトごとに別のレンダラプロセスを使うこと。別サイトのデータが同じプロセスのメモリに載らない。
DOMHTML から作る文書の木。要素・文字・コメントがノードで、属性は要素に付く。JS の document がその根。
CSSOM・計算済みスタイルCSS の規則の木と、各ノードに全プロパティの値を確定させたもの。カスケード（出所→詳細度→順序）と継承で決まる。
レイアウト各ボックスの位置と大きさを px で決める処理。幅は親から、高さは中身から。変更部分だけやり直す。
レイヤー・合成別々に動く部分を別の層に描き、コンポジタが重ねて1枚にする。スクロール、動画、transform・opacity のアニメーションは合成だけで動く。
イベントループタスクを1つ実行 → マイクロタスクを全部 → 必要なら描画、の繰り返し。メインスレッド1本で回る。
V8・JITChromium の JS エンジン。バイトコード（Ignition）で始め、よく走る関数ほど段階的に機械語にする（Sparkplug → Maglev → TurboFan。2026 年時点の名前）。
MSE・SourceBufferMedia Source Extensions。JS が appendBuffer で動画・音声のバイト列を入れる口。buffered に再生可能な区間が増える。
PTSPresentation Time Stamp。各フレームの表示時刻。currentTime（音声の時計）が追いついたフレームを合成に出す。
