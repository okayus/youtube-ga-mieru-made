IP

DNS が番号を返すと、ブラウザの最初のパケットは宛先 142.250.196.110 を書いた IP ヘッダを付けて家を出る。IP は、宛先の番号だけを頼りにルーターからルーターへパケットを 1 個ずつ渡す約束ごとで、届くことも順番も保証しない。この章では、IPv4 ヘッダの 20 バイト、番号の範囲の書き方と配り方、128 ビットの IPv6、ホップごとに変わる欄と変わらない欄、区間ごとの大きさの上限（MTU）、そして ping と traceroute を支える ICMP を順に見る。

1IPv4 ヘッダ — 20 バイトに決まった欄が並ぶ

RFC 791（1981 年）20 バイトプロトコル 17 = UDP

IP パケットは、20 バイトのIPv4 ヘッダと中身でできている。途中のルーターが読むのはヘッダだけ。宛先と送信元の番号、全体の長さ、残りの寿命（TTL）、中身の種類、検算の値が決まった位置に入る。

欄の位置と長さは 1981 年の RFC 791 から変わらず、2 バイト目は後に DSCP と ECN に定義し直された。Wireshark などでパケットを取ると、図の 20 バイトと各欄の値を並べて見られる。IPv6 では欄を整理し直した（3「IPv6」）。

2アドレスとサブネット — /n で範囲を書き、切り分けて配る

CIDR（1993 年）IANA → RIR → ISP約 43 億個

IPv4 アドレスは 32 ビットで、約 43 億個しかない。番号は先頭の n ビットが共通の範囲（/n）で書いて配り、経路表に載せる。範囲は IANA から地域の登録機関、ISP、家へと切り分けられる。

範囲の持ち主は whois や RDAP で調べられ、142.250.0.0/15 は ARIN に登録された Google の範囲。マスクで「同じネットワークか」を決める手順は第14章、いちばん長く一致する行を選ぶ手順は第16章。

3IPv6 — 128 ビットの番号と 40 バイトのヘッダ

RFC 8200/56 と /64SLAAC

IPv6 は番号を 128 ビットに広げた IP の新しい版。家には /56 などの範囲が丸ごと配られ、機器は自分で番号を作る。ヘッダは 40 バイトの固定長に整理され、NAT を使わずに端から端まで同じ番号で通信する。

ブラウザは DNS で A と AAAA の両方を引き、IPv6 で先に接続を試し、すぐに応答が無ければ IPv4 も試す（Happy Eyeballs、RFC 8305）。IPoE の家（第15章）では、YouTube への接続の多くが IPv6 になる。

4ホップごとに起きること — 変わる欄と変わらない欄

ルーター 9 台（例）TTL 64 → 55宛先は 142.250.196.110 のまま

家から YouTube のサーバーまで、パケットは数台から十台ほどのルーターを順に渡る。どのルーターも第14章と同じ手順で転送し、そのたびに TTL・チェックサム・MAC が変わる。宛先 IP は最後まで変わらない。

1 ホップの遅れは、光が線を進む時間（1 km あたり約 5 µs）、送り出す時間、転送の処理（数 µs 程度）、待ち行列の待ちの合計。混んでいなければ距離の分が大半を占め、国内の YouTube のサーバーまでの往復は数 ms〜十数 ms。

5MTU と断片化 — 区間ごとの大きさの上限

Ethernet 1,500PPPoE 1,492IPv6 の最小 1,280QUIC 1,200

1 区間で運べる IP パケットの最大の長さが MTU。Ethernet は 1,500 バイトで、トンネルを通る区間はヘッダの分だけ小さい。途中に小さい区間があれば、パケットは分けられるか、捨てられて知らされる。

MTU の不一致による不調は、小さいパケットは通るのに大きいものだけ消えるのが特徴。Linux の tracepath は途中の MTU を表示し、Windows では ping に -f（DF を立てる）と -l（大きさ）を付けて、通る最大の長さを探せる。

6ICMP — ping と traceroute

プロトコル 1Echo 8 / 0Time Exceeded 11

ICMP は IP の上で送る連絡用のメッセージ。宛先に応答を頼んで往復時間を測るのが ping。TTL を 1 から順に増やして送り、途中のルーターが返す「TTL 切れ」を集めて道を並べるのが traceroute。

Windows の tracert は UDP の代わりに Echo Request を使う。2026 年 10 月 12 日に家庭の光回線から www.youtube.com へ ICMP で測ると 6 ホップ、往復は最小約 7 ms だった。ホップの数は回線の方式で変わる。

7まとめ — 番号だけを頼りに、1 個ずつ渡す

  1. IPv4 ヘッダは 20 バイト。宛先と送信元の番号、全長、TTL、中身の種類（プロトコル）、ヘッダだけの検算が決まった位置に入る（1）。
  2. 番号は /n の範囲で書いて配り、まとめて広告する。IANA → RIR → ISP → 家と切り分けられ、IPv4 の在庫は 2011 年に尽きた（2）。
  3. IPv6 は 128 ビット。家には /56 などの範囲が配られ、LAN は /64 で、機器は RA を見て番号を自分で作る。ヘッダは 40 バイトの固定長で、NAT を使わない（3）。
  4. ルーターを越えるたびに TTL は 1 減り、チェックサムと MAC は区間ごとに変わる。宛先 IP は端から端まで変わらない（4）。
  5. 道全体で通せる大きさは最も小さい区間の MTU。IPv4 は DF が 0 なら途中で分け、1 なら捨てて ICMP で知らせる。IPv6 と QUIC は途中で分けない前提で大きさを選ぶ（5）。
  6. ICMP は IP の連絡用のメッセージ。ping は往復時間を測り、traceroute は TTL を 1 ずつ増やして Time Exceeded を集め、道の上のルーターを並べる（6）。
IPv4 ヘッダパケットの先頭に付く 20 バイトの欄の並び（RFC 791）。版・全長・識別子・フラグ・TTL・プロトコル・チェックサム・送信元・宛先など。
TTL ／ ホップリミット通ってよいルーターの残り台数（8 ビット）。1 台ごとに 1 減り、0 で破棄。初期値は Linux・macOS が 64、Windows が 128。
プロトコル番号中身の種類。1 が ICMP、6 が TCP、17 が UDP。IPv6 では次ヘッダの欄で、ICMPv6 は 58。
ヘッダチェックサムヘッダを 16 ビットずつ足し、あふれた桁を足し戻して反転した値。ヘッダだけを守る。IPv6 には無い。
CIDR・プレフィックス先頭 n ビットが共通の範囲を /n で書く方式（1993 年）。/24 は 256 個、/15 は 131,072 個、/32 は 1 個。
RIR地域ごとに番号を配る 5 つの登録機関（APNIC、ARIN、RIPE NCC、LACNIC、AFRINIC）。日本は APNIC の下の JPNIC。
IPv6128 ビットの番号の IP（RFC 8200）。16 ビットずつ 16 進で書き、0 の組の連続を :: に省く。ヘッダは 40 バイト。
SLAACRA で知らされた /64 に、機器が自分で決めた後半 64 ビットを付けて番号を作る方式（RFC 4862）。
MTU・経路 MTU1 区間で運べる IP パケットの最大長。Ethernet 1,500、PPPoE 1,492（フレッツの推奨は 1,454 以下）、IPv4 over IPv6 1,460、IPv6 の最小 1,280。道全体の最小が経路 MTU。
ICMPIP の誤りの知らせと問い合わせのメッセージ（プロトコル 1）。Echo 8 / 0、到達不能 3、TTL 切れ 11。
